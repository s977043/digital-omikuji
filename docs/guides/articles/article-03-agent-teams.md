# 記事3：AIを「相棒」から「チーム」に進化させる—Agent Teamsと役割設計

## 第1部：なぜ“チーム化”が流行しているのか

近年の開発現場では、単一のAIアシスタントより、複数エージェントを役割分担させる運用が増えています。背景は明確で、複雑な開発タスクは「実装」だけでなく、分解・批評・記録が同時に必要だからです。

複数セッションを独立コンテキストで並列実行し、最後に統合する考え方は、AIを「道具」から「協働メンバー」に近づけます。ただし、並列化は自動的に品質を上げません。統合時の引き継ぎ設計が未熟だと、むしろ混乱が増えます。

## 第2部：役割設計の型（Lead / Implementer / Critic / Scribe）

### Lead（人間推奨）
- 目的、制約、受入条件、変更境界を固定する。
- タスク分割と優先順位を決める。

### Implementer
- 実装と局所最適化を担当する。
- 仕様外に広げない。

### Critic（Devil’s advocate）
- 仕様逸脱、セキュリティ、運用リスク、影響範囲漏れを先回りで指摘する。

### Scribe
- PR説明、根拠、再現手順、計測結果を整理する。
- レビューの認知負荷を下げる。

### 具体例
- バグ修正：Implementerが修正、Criticが再現条件と回帰リスクを検査、Scribeが再現手順を記録、Leadがマージ判断。
- リファクタ：Leadが非機能目標を定義、Implementerが構造整理、Criticが挙動差分を検証、Scribeが変更境界を文書化。
- 機能追加：Leadが価値仮説と受入条件を設定、Implementerが実装、Criticが悪用ケースを点検、Scribeが観測指標をPRに添付。

## 第3部：チーム開発として事故らせない（権限・責任・ガードレール）

### 運用チェックリスト

- [ ] **権限境界**：危険操作（依存追加、本番設定変更、認可変更）は手動承認
- [ ] **変更境界**：エージェントごとに触ってよいディレクトリを限定
- [ ] **証拠の義務化**：テスト、ベンチ、ログ、スクリーンショット（可能なら）を添付
- [ ] **監査可能性**：誰が何を判断したか、意思決定の履歴を残す
- [ ] **最終責任**：価値とリスクの最終判断者を人間に固定

エージェントが自律的にコードへ変更を提案・適用できる時代では、ガードレールは「補助策」ではなく運用の本体です。

### 反例・限界
「チーム化すれば常に速くなる」とは限りません。小規模タスクでは調整コストが上回り、責任境界が曖昧になると監査負荷も増えます。役割設計は、タスク規模とリスクに応じて可変にする必要があります。

## セルフレビュー（詳細）

### 1) 主張の明確性
- 「AIを個別ツールではなくチームとして運用する」主張は、役割モデルとチェックリストで具体化できている。
- ただし、どの規模のタスクでチーム化すべきかの判断基準を追記すると実務導入しやすい。

### 2) 根拠の配置
- 公式機能への言及は抑制的で断定を避けており、誤読リスクは低い。
- 一方で、各役割の成果物（例: Criticのリスクメモ）を明示すると検証可能性が高まる。

### 3) 反例・限界の扱い
- 小規模タスクでは調整コストが勝る反例を記載しており、バランスは良い。
- さらに、責任境界が曖昧な場合に発生する監査コスト増を運用失敗例として補強できる。

### 4) 実務適用の具体性
- チェックリストは使いやすいが、開始時テンプレ（Lead指示文）がない。
- 導入時は「目的/境界/期限/証拠」の4項目テンプレを併用すると効果が高い。

## 改善反映
- 本改訂で、チーム化適用の判断軸（タスク規模とリスク）をセルフレビューで明示した。
- Lead開始テンプレ（目的/境界/期限/証拠）を追加運用として提案した。
