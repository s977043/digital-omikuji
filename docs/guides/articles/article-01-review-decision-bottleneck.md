# 記事1：AIでPRが増えるほど「レビューと意思決定」が詰まる理由

## 第1部：現象の整理（なぜ“速く書ける”のに“遅く進む”のか）

AIエージェントの導入で、Issue→修正→PR作成のリードタイムは短くなりました。とくに GitHub 上で AI が開発フローに組み込まれることで、PRの作成頻度と更新頻度はさらに上がりやすくなります。

一方で、実務の体感としては「実装は速いのに、全体としては前に進まない」ことが増えます。これは開発フローの律速が、実装からレビューと意思決定へ移ったためです。研究・事例でも、agent-authored PRは「すぐマージ」されるか「レビュー往復が長期化」するかの二極化が観測されています。

要するに、AIが生産した差分の量が増えた結果、チームの希少資源である「高品質な判断」が不足し始める、という構造です。

## 第2部：ボトルネックの正体（レビュー工数ではなく“判断コスト”）

レビューが詰まる理由は、単純な工数不足だけではありません。実際には次の4つの判断コストが重なります。

### 1. 意図復元コスト
PR本文に「目的・非目的・受入条件」がないと、レビュワーが仕様を再構築する必要があります。読む時間ではなく、**解釈する時間**が増えます。

### 2. 影響範囲の推定コスト
変更が広く散在しているPRは、正しさ以前に「どこまで確認すれば十分か」の線引きが難しくなります。レビューの終わりが見えない状態になります。

### 3. 証拠（テスト/観測）の信頼コスト
テストケースが多くても、仕様保証や運用リスクの低減につながらないと安心材料になりません。結果として「結局、人間が全文を読む」状態が残ります。

### 4. 意思決定の集中
「この変更は価値に効くか」「いま入れるべきか」という経営・プロダクト寄りの判断が、最終的にPRレビューへ集中します。実装速度が上がるほど、この最終関門の負荷が上がります。

## 第3部：打ち手（レビューを“人力作業”ではなく“システム”にする）

1. **PR粒度の規律**
   - 変更は小さく独立させる。
   - PRテンプレに「何を変えないか」を明記する。

2. **受入条件のテンプレ化**
   - Given/When/Then で成功条件を定義する。
   - 非機能（性能、セキュリティ、運用）も同じテンプレに含める。

3. **リスクベース・レビュー**
   - 低リスク変更は自動化中心。
   - 高リスク変更はレビュー観点を固定し、人間判断を集中させる。

4. **証拠ドリブン文化**
   - テスト結果、ベンチマーク、ログ、観測指標（SLI/SLO）をPRに添付する。
   - 主張だけでなく、再現可能な証拠をセットにする。

5. **AIの役割分離**
   - 実装AIと批評AI（Critic）を分ける。
   - 反例・影響範囲・失敗シナリオを先に掘り、人間は最終意思決定へ集中する。

### 反対意見・限界
「レビューを自動化しすぎると、人間が文脈を失って危険」という反対意見は妥当です。したがって、最終判断責任を人間に固定し、AIは判断を補助する証拠生成に寄せる設計が必要です。

## セルフレビュー（詳細）

### 1) 主張の明確性
- 「実装速度向上に対してレビュー判断が律速になる」という主張は、第1部→第2部の流れで一貫している。
- ただし、読者が再現しやすいように判断コストを定量化する観測項目（例: レビュー往復回数）を明示すべき。

### 2) 根拠の配置
- 初稿では「出典明記の必要性」を書いているが、本文に根拠管理の型がない。
- 改善として、PRテンプレに「主張ごとの出典メモ欄」を追加する運用例を本文へ追記する余地がある。

### 3) 反例・限界の扱い
- 「自動化しすぎの危険」を明記しており、過度な自動化へのブレーキは示せている。
- 一方で、低リスク領域では自動化が有効という条件付き整理を追記すると誤解を避けられる。

### 4) 実務適用の具体性
- 打ち手5点は実務に落とせるが、導入順序がない。
- 導入順を「PR粒度→受入条件→証拠添付→リスクベース→役割分離」と示すと実装しやすい。
