# Cursor / AI セルフレビュー・チェックリスト（Digital Omikuji）

このmdは「AI生成PRで起きがちな事故」を、人間の勘に頼らず機械＋手順で潰すためのものです。

- 最優先は「意図と差分の一致」と「残骸ゼロ」。
- 目視は最後。機械的に担保できるものはCIへ寄せる。

---

## 使い方（最短で回す）

### レビュー深度の選び方

- ゲート（30秒）: 全PRで必須
- クイックスキャン（5分）: Cursor/AIが触ったPRは基本ここまで
- ディープ（必要時）: リファクタ大、API/型/依存/移動/分割/統合、境界変更、性能やセキュリティに関わる変更

### セルフレビューの出力ルール

- ✅は書かなくてよい。NG/要確認だけをPR本文に列挙する（後述テンプレ参照）
- 「将来使うかも」「念のため残す」は原則不採用（削るか、理由をPR本文に書く）

---

## 1. ゲート（30秒）— 全PR必須

- [ ] PR説明と差分の意図が一致している（余計な変更が混ざっていない）
- [ ] 追加した定義（関数/クラス/型/ファイル）に利用箇所がある  
      例外: 将来利用目的なら、PR本文に「理由」と「追跡チケット/期限」を書く
- [ ] CIが緑（ない場合はローカルで代替コマンドを実行して結果を残す）
- [ ] 秘密情報（キー/トークン/個人情報）が差分に混入していない
- [ ] 管理外ファイル（`node_modules/`, `**/*.lock`, `.env*`, `secrets/`）を触っていない

---

## 2. クイックスキャン（5分）— 迷ったらここまで

### 2.1 命名: repo語彙に寄せる（AIは一般論に逃げがち）

- [ ] 同概念の既存語彙と一致している（draw/fortune/history など）
- [ ] Hook は `useXxx`、画面は `app/` のルート名、UI部品は `components/` の責務に合う名前
- [ ] 略語・表記ゆれがない（ID/Ids、E2E/e2e、i18n など）
- [ ] 単数/複数が適切（Result/Results、History/Histories など）
- [ ] 「広すぎる名前」が増えていない（Util/Helper/Common の増殖）

命名レビューの実務ルール:

- 「このrepoで検索するときに人が想起する単語」を優先する
- 新語彙を導入するならPR本文に「既存語彙ではダメな理由」を1行書く

### 2.2 残骸: 未使用コード/ファイルをゼロにする（事故の本丸）

- [ ] 新規追加した関数/クラス/型の呼び出し元を追跡できる
- [ ] 未使用exportがない（公開APIを無駄に増やしていない）
- [ ] リファクタで不要になった関数/クラス/ファイルが削除されている
- [ ] 旧実装（old/legacy/tmp など）や旧テスト/モックが残っていない
- [ ] `console.log` などのデバッグログやコメントアウトコードが残っていない

推奨コマンド（ローカル/CIのどちらかで必ず）:

- `git status`: 意図した削除（D）が入っているか
- `rg -n "OldSymbol|旧関数名|旧クラス名" .`: 旧名の残存チェック
- `rg -n "TODO|TEMP|HACK" .`: 置き土産チェック

### 2.3 境界: 依存方向と公開面積（AIは平気で壊す）

- [ ] 依存方向が方針通り（`app` → `components/hooks/utils`、`hooks` → `utils`）
- [ ] `utils` が `app`/`components` に依存していない
- [ ] UI から実機API（センサー/触覚/音）を直接呼んでいない（`utils`/`hooks` 経由）
- [ ] 「共通化」の名で密結合を増やしていない（雑な utils 化）
- [ ] public API（export/公開関数/外部境界）が意図せず増えていない

### 2.4 AIっぽいバグ: 短時間で刺すチェック

- [ ] 境界条件（null/空/0/上限/例外）を踏んでいる
- [ ] エラー処理が握りつぶしになっていない（ログだけ出して成功扱い等）
- [ ] 非同期のawait漏れ、順序、状態更新タイミングが正しい
- [ ] React Hookの依存配列とcleanupが正しい（センサー/タイマー/アニメーション）
- [ ] セキュリティ: 入力検証、権限、秘密情報ログが適切
- [ ] パフォーマンス: 再描画増、無駄な再計算/コピー、不要なデータ取得がない

---

## 3. ディープ（必要時）— 大きい変更だけ

### 3.1 変更範囲の整合（ズレ検知）

- [ ] 影響範囲が妥当（`app`/`components`/`hooks`/`utils` をまたぐ変更が必要最小限）
- [ ] ルーティング変更時に `app/` の画面名・遷移・リンクが整合している
- [ ] リネーム/移動の整合（import/export、参照更新、バレル export）
- [ ] 互換性: 既存の呼び出しが壊れていない（戻り値/例外/型/仕様など）

### 3.2 仕様と失敗モード

- [ ] 「成功/失敗」の定義が明確（例外、戻り値、UI状態）
- [ ] 実機APIの例外（権限/センサー未対応/音声失敗）に備えている
- [ ] 観測可能性（ログ/Sentry）が必要なら入っている

### 3.3 テスト戦略（最低ライン固定）

- [ ] unit/integration が通る（`pnpm test`）
- [ ] Web E2E が必要なら通る（`pnpm test:e2e:web`）
- [ ] 新規追加/修正したロジックにテストがある（境界・分岐が増えたら優先）

## 4. Glossary（repo語彙表）— 命名ブレを消す

この表は「好み」ではなく「プロジェクトの正解」を固定するためのもの。必要に応じて更新する。

### 4.1 レイヤと責務（Digital Omikuji）

- Screen（`app/`）: 画面単位の構成とルーティング。ロジックは `hooks` に寄せる
- Component（`components/`）: 表示とユーザー操作のUI。副作用は最小限
- Hook（`hooks/`）: 状態管理と抽選ロジック。実機依存は `utils` に委譲
- Utility（`utils/`）: AsyncStorage/サウンド/触覚など副作用・プラットフォーム境界
- Data/Types（`data/`, `types/`）: 固定データと型定義

### 4.2 ドメイン語彙（例）

- `OmikujiResult`: 抽選結果のデータ構造
- `FortuneLevel`: 運勢レベル（`daikichi` など）
- `HistoryEntry`: 保存される結果（現状は `OmikujiResult` の別名）
- `ResultAction`: 結ぶ/持ち帰るの行動（`tie`/`keep`）

## 5. 機械化マップ（CI/フックに寄せる）

### 5.1 まずCIで必須にしたいもの

- `pnpm test`
- `pnpm lint`
- `pnpm lint:md`（ドキュメント変更時）
- `pnpm test:e2e:web`（Web UI/導線変更時）
- `pnpm build`（Webビルドに関わる変更時）

### 5.2 残骸を機械で潰す候補

- 未使用import/変数: ESLint ルール
- 未使用export: lintルールや専用ツール（導入できるなら）
- 未使用ファイル: 専用ツール（TS系なら knip/ts-prune 等）
- 旧名残存: `rg` をCIジョブ化（キーワードはPRごとに変わるので、手順として固定）

---

## 6. プロジェクト固有チェック（Digital Omikuji）

### 6.1 Expo/実機API

- [ ] 触覚/センサー/サウンドの呼び出しが `utils` 経由になっている
- [ ] 権限・未対応デバイス・失敗時の挙動が破綻しない
- [ ] リソース解放や停止処理（音/センサー）が必要なら入っている

### 6.2 UI/アニメーション

- [ ] NativeWindの `className` が主体（`style` の乱用なし）
- [ ] Moti/Reanimated のアニメがWebでも破綻しない
- [ ] 画像/アセットのサイズが過剰でない

### 6.3 i18n

- [ ] 追加文言は `i18n/locales/ja.json` と `i18n/locales/en.json` に両方追加
- [ ] 既存キーの再利用が妥当（誤用や意味ズレがない）

### 6.4 履歴/日次制限

- [ ] 履歴の順序（最新が先頭）が崩れていない
- [ ] 1日1回制限とリセット動作が矛盾していない
- [ ] `ResultAction` の更新と表示状態が整合している

## 8. PR本文テンプレ（セルフレビュー結果の書き方）

以下をPR本文に貼り、NG/要確認だけ残す。

```md
## セルフレビュー結果（NG/要確認のみ）

- 変更意図 vs 差分:
  - (例) Aの修正のはずがBも触れていた → Bは別PRに分離

- 命名:
  - (例) `drawX` はrepo内では `drawFortune` が主流 → 命名修正予定

- 残骸:
  - (例) `FooManager` が参照されていない可能性 → 参照追跡/削除対応

- 境界/依存:
  - (例) UIから直接 `expo-haptics` を呼んでいた → `utils` 経由に修正

- 機械検証ログ:
  - pnpm test: ✅/❌（ログや結果を1行）
  - pnpm test:e2e:web: ✅/❌
  - pnpm lint: ✅/❌
  - pnpm build: ✅/❌

- 動作確認:
  - (例) 実機でシェイク→抽選→履歴表示まで確認
```
